# Zero to One Workflow

---

## 階段零、開發前置作業 (所有人都要做)

在開始任何專案前，請確保你的電腦已經安裝以下基礎工具：
1. **Node.js**：運行前端與後端 JavaScript/TypeScript 的必備環境。
2. **Git**：版本控制工具，用來記錄與同步程式碼的修改歷史。
3. **VS Code**：推薦的程式碼編輯器。建議安裝 `Prettier` 與 `ESLint` 相關擴充套件以輔助排版。
4. **Docker Desktop**：用來在本機端運行資料庫環境。

---

## 階段一：專案基礎設施建置 (由 Repo 負責人執行一次即可)

負責人請依序完成以下專案骨架建置，完成後將代碼推送到 GitHub，其他組員只需將專案下載 (Clone) 到本地端即可。

### 1. 建立空專案與基礎架構
* **版本控制初始化**：建立專案主資料夾，並初始化 Git 儲存庫。
* **前端環境建立**：建立基於 Vite + React + TypeScript 的前端專案資料夾。
* **後端環境建立**：建立 Node.js 後端資料夾，並安裝 Express、Socket.io、MongoDB 等必備套件，同時配置好 TypeScript 環境。

### 2. 設定本地資料庫 (Docker)
* 在專案根目錄建立 Docker 容器設定檔 (`docker-compose.yml`)。
* 確保指定使用的 MongoDB 映像檔版本（如 7.0）明確支援雙系統架構 (`linux/amd64` 與 `windows`)，並設定好資料掛載 (Volumes)，以免每次重啟 Docker 遺失測試資料。

### 3. 設定自動排版與攔截器 (Husky + Lint-Staged)
* 安裝並初始化 Husky 與 Lint-Staged。
* 設定 Git 提交前的攔截機制 (pre-commit hook)：確保未來任何人在提交程式碼前，系統都會自動呼叫 Prettier 進行排版，並用 ESLint 檢查語法錯誤。有錯就直接擋下不給提交。

*(負責人完成以上建置並推送到 GitHub 的 main 分支後，專案的地基就打好了！)*

## 階段二：建立 AI 溝通規則 (存放於專案根目錄)

為了讓 AI 聽懂我們的話，負責人需在專案內建立這兩份「規則書」。**全體組員在呼叫 AI 時都必須使用它們。**

### 1. 全域架構規定 (`AI_CONTEXT.md`)
這份文件定義專案的邊界，請包含以下內容：
> 專案名稱：Dynamic Status Node Calculator
> 開發限制：
> 1. 前端使用 React + Zustand + Tailwind CSS。
> 2. 後端使用 Node.js + Express + Socket.io。
> 3. 資料庫為 MongoDB。
> 4. 嚴格遵守 TypeScript，禁用任何未定義的型別。
> 5. **業務邏輯鐵律**：數值計算引擎絕對不可有任何預設非 0 數值（若無輸入，預設值就是 0）。

### 2. 開發指令模板 (`docs/ai-prompts.md`)
這份文件是每日呼叫 AI 寫邏輯時的起手式模板：
> **測資生成模板**：
> 「請根據需求撰寫單元測試。測試必須包含邊界條件。」

## 階段三：新手每日開發流程 (Daily Dev Loop)

這是你每一天寫程式的標準循環。**每次開發新功能前，請務必從 Step 1 開始。**

### Step 1: 獲取最新進度與啟動環境
* 確保你的本地端處於 `main` (主幹) 分支，並從 GitHub pull 團隊最新的程式碼。
* 啟動背景的 Docker 資料庫服務，以及前端的開發測試伺服器。

### Step 2: 建立自己的工作分支 (Feature Branch)
* **絕對不要在 `main` 分支上直接修改程式碼！**
* 每次開發新功能，請從 `main` 切換並建立一條以該功能命名的專屬分支。

### Step 3: 給 AI 看規則書 (Context Sync)
打開你習慣的 AI 工具（如 Gemini、Antigravity 或 Claude），**第一句話請要求它閱讀規則**：
* 告訴 AI：「我要開始開發新功能了。請先閱讀 `AI_CONTEXT.md` 與 `docs/ai-prompts.md` 的內容（將內容貼給它）。請回覆『規則已確認』，先不要寫任何程式碼。」

### Step 4: 測試驅動開發 (TDD) - 讓 AI 先寫考卷
* **不要讓 AI 直接寫功能邏輯。** * 請 AI 根據你要開發的功能（參考 `ai-prompts.md` 的模板），先寫出一份「單元測試程式碼」。
* 將這份測試程式碼放入專案中並執行測試，此時測試結果必須是**失敗（紅燈）**的，因為真正的功能還沒寫。

### Step 5: 讓 AI 寫實作代碼
* 告訴 AI：「測試寫好了，現在測試失敗。請幫我實作這個功能的邏輯，目標是讓剛剛的測試通過。」
* 將 AI 給你的邏輯程式碼貼入專案，再次執行測試。如果測試依然失敗或報錯，請直接將錯誤訊息複製丟給 AI，要求它修復，反覆此動作直到測試顯示**成功（綠燈）**。

### Step 6: 存檔與防線檢查 (Git Commit)
* 當測試通過，且功能在畫面上運作正常時，將程式碼加入暫存區並進行提交 (Commit)。
* 此時，專案內建的 Husky 攔截器會自動啟動，幫你做最後的排版與語法檢查。如果被攔截器報錯擋下，請根據提示（或請 AI 幫忙）修改後再次提交。

### Step 7: 推送與發起合併 (Pull Request)
* 將你開發好的專屬分支推送到 GitHub 雲端。
* 在 GitHub 網站上發起一筆 Pull Request (PR) 請求，申請將你的新功能合併回 `main` 主幹。
* 在 PR 頁面中，清楚填寫你完成了什麼功能，並指定另外兩位組員來審查你的程式碼。

### Step 8: 程式碼審查 (Code Review) 與合併
* **組員互相把關**：被指定的組員需檢查程式碼邏輯，如果有看不懂的地方，可以將該段程式碼丟給 AI 輔助解讀，尋找是否有潛在漏洞。
* 確認一切無誤後，即可同意合併。你的新功能就會正式加入專案中！
* 開發者回到本地端，切換回 `main` 分支並拉取最新代碼（回到 Step 1），準備迎接下一個挑戰！
